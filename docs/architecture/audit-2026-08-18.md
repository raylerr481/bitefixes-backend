# BiteFixes Backend Architecture Audit — 2026-08-18

## Current state

The backend already contains the core entities required by the Bitey 2.0 target architecture: companies, business profiles, domains, capabilities, intents, knowledge, needs, requirements, solutions, actions, agents, tools, workflows, subscriptions, leads, quotes, tickets, conversations and messages.

The main architectural gap is not missing database entities; it is the runtime integration and consistency between those entities and the application layer.

## Findings

1. `decision_engine.py` already loads company context, AI scope, intent, service and workflow. This is aligned with the intended Company/Tenant → Business Context → AI Scope → Intent → Service → Workflow direction.
2. `company_service.py` assembles business profile, industries, business models, functions, subscription, AI scope, domains, capabilities, services and knowledge, but performs many independent queries and does not expose a stable typed context contract.
3. `main.py` currently exposes only chat, customers and tickets routers even though the database contains substantially broader business capabilities.
4. CORS is configured as `allow_origins=["*"]` together with credentials, which should not be used in production.
5. The database has RLS enabled on all public tables, but most tables have no public/authenticated policies. The backend can continue to use the privileged server connection, but API exposure should be intentional and tenant-scoped before frontend direct access is enabled.
6. `tickets` still contains legacy Spanish columns alongside the normalized English columns. `tickets_backup` is clearly a migration artifact and should not be part of the operational model.
7. `services` contains inactive legacy duplicates. The active catalog is already represented by the newer rows and should be preserved while legacy rows are retired through controlled migration rather than destructive deletion.
8. `sinonimos_ia` remains a legacy Spanish-named table while the newer semantic subsystem exists. Migration should be incremental; do not remove it until all intent resolution paths use the semantic model.
9. Semantic tables are currently empty except for a semantic version, so the semantic subsystem is infrastructure rather than an active source of production decisions.
10. The database already implements the planned `Intent → Need → Requirement → Solution → Action` chain through foreign keys and relation tables, so new duplicate tables are unnecessary.

## Recommended implementation order

1. Stabilize the application context contract and database access layer.
2. Add a read-only business context API for diagnostics and integration tests.
3. Add tenant-aware domain/capability/intent/service/knowledge endpoints behind the backend boundary.
4. Make decision execution consume a normalized context object rather than repeatedly querying tables.
5. Add workflow persistence/runtime synchronization.
6. Add CRM orchestration for leads and quotes.
7. Migrate legacy naming and duplicate catalog rows only after runtime compatibility tests pass.
8. Tighten CORS and tenant-aware authorization before exposing new endpoints to browser clients.

## Safety principle

Do not delete existing production data during this phase. Prefer additive code changes, compatibility layers, migrations, and deprecation markers. Production schema changes must be reversible and verified after application changes.
